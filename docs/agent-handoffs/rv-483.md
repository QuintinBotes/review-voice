## Goal and scope

Implement issue #483: a deterministic relevance check, from GitHub reads only, that decides whether a pull request concerns the configured team before any agent runs. It is used by a new `relevance` command and by the queue, which skips team-only pull requests that match no signal and can surface unrequested pull requests that do match. It is off by default; with no `queue.relevance` block, behaviour is unchanged.

### Configuration (`queue.relevance`, parsed where `queue` is parsed in `src/policy/load.ts` and typed in `src/queue/config.ts`)

```yaml
queue:
  relevance:
    teams: [org/slug]            # default: queue.teams. CODEOWNERS owners are matched as @org/slug, case-insensitive
    min_owned_share: 0.2         # 0..1, share of changed lines (additions + deletions) in files a team owns
    ignore_owned_paths: []       # globs; owned files matching these do not count toward the share
    paths: []                    # globs; any changed file matching one is a signal
    added_line_patterns: []      # regular expressions (case-insensitive) matched against added lines of the file patches
    authors: []                  # logins; the author being one is a signal
    keywords: []                 # words matched case-insensitively, whole word, against title and description
    discover:                    # optional; absent means no discovery
      updated_within_hours: 24
      max_pulls: 50
```

Validate it like the neighbouring keys: unknown keys warn, bad values (a share outside 0..1, an invalid regular expression, a non-positive number) are ignored with a warning naming the key, and the block is listed in the known-keys table (`queue: [...]`, around line 209). Reuse the repository's existing glob matcher; do not add a dependency.

### The check (new module, for example `src/queue/relevance.ts`)

Input: repository, pull number, and the pull request already read (title, body, author, base sha). Reads, all through the existing read-only `GitHubClient` and honouring its allowlist:
- the files list with patches (`/pulls/{n}/files`, paginated, capped; when the cap is hit, say so in the result as `truncated: true`);
- CODEOWNERS at the base sha, from the first of `.github/CODEOWNERS`, `CODEOWNERS`, `docs/CODEOWNERS` that exists (GitHub's order). Use GitHub's matching rules: the last matching line wins, `#` comments, patterns relative to the root unless they have no slash, a trailing `/` means a directory, and `*` and `**` work as GitHub documents them. A file with no CODEOWNERS, or one that cannot be read, gives an owned share of null and the signal reason says why. That is never an error.

Signals, each `{kind, detail}`: `owned` (with the share, to two decimals, and the teams matched), `path` (the glob and the first file), `added_line` (the pattern, file and head line), `author`, `keyword` (the word). `relevant` is true when any signal matches. Output: `{relevant, signals, ownedShare, truncated, reasons}`, where `reasons` is human text listing the signals, or why none matched.

### Command

`review-voice relevance --pr <n> [--repository owner/repo]` prints that JSON. The exit code is 0 whether or not the pull request is relevant, and 2 for a bad invocation or a credential problem. Add the help entry in `src/help.ts`, matching its neighbours, and wire the command into the CLI the way `queue` is wired.

### Queue (`src/queue/queue.ts`)

- When `queue.relevance` is configured, a candidate whose sources are only `team` (no `requested`, `assigned`, `follow-up` or `dismissed`) and that is not relevant gets `{kind: 'skip', rule: 'relevance'}`. Carry the reasons on the entry, for example in a new optional field on the skip action, so the queue and watch output show why. Run this after the cheaper skip rules, so a draft or a bot is skipped without reading files.
- A personal request, an assignment, a follow-up or a dismissed review is never filtered by relevance.
- Discovery, only with `discover` configured: search recently updated open pull requests in each allowlisted repository, updated within `updated_within_hours`, at most `max_pulls` in total (extend `SearchSource` and `searchPullRequests` with a new source in the same style). Drop the ones already in the queue, the author's own, and those the existing skip rules would skip. Run the relevance check on the rest. A relevant one is listed with a new action `{kind: 'surface', signals}` and a new source `discovered`. **A surface entry is never reviewed, posted or recorded as handled.** `watch` must treat it as report-only: print it in the pass output and do nothing else. It does not count toward `max_per_pass`.

## Acceptance criteria

- Without `queue.relevance`, the queue output for the existing queue tests is byte-identical (the existing `test/queue.test.mjs` passes unchanged).
- CODEOWNERS matching: last match wins; `*.js` with no slash matches at any depth; `/docs/` matches only the root docs directory; `**` across directories; comments and blank lines are ignored; a line with no owners un-owns the path.
- Owned share: with a team owning one of two changed files, carrying 30 of 100 changed lines, the share is 0.30, which is relevant at `min_owned_share: 0.2` and not at 0.5. An ignored owned path contributes 0. Missing CODEOWNERS gives `ownedShare: null` with a reason, not an error.
- Each of `path`, `added_line`, `author` and `keyword` alone makes a pull request relevant, with its detail. A keyword matches a whole word only: `extract` does not match `extraction` unless it is configured.
- Queue: a team-only, irrelevant pull request is `skip` with rule `relevance` and its reasons. The same pull request with a personal request is reviewed. A draft is skipped as `drafts` before any files are read; assert on the fake client that no files call was made.
- Discovery: a relevant unrequested pull request appears as a `surface` entry with source `discovered`. It never appears as `review`. `watch --once` with a fake client posts nothing and records nothing for it. Discovery respects the allowlist and `max_pulls`.
- `relevance --pr` prints the JSON shape above, and exits 2 on a missing `--pr`.
- Config validation: an invalid regular expression and a share of 1.5 are ignored with warnings naming the key.
- Tests: a new `test/issue-483-queue-relevance.test.mjs` covers every criterion above using the existing fake GitHub client patterns in `test/queue.test.mjs`.
- `npm run verify` passes, apart from failures that also occur on the untouched baseline. On this machine the process-kill timing tests in `test/issue-277-stoppable-commands.test.mjs`, `test/command-runner.test.mjs` and `test/agent-runner.test.mjs` can fail under load and pass alone.
