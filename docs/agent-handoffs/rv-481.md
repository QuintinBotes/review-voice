## Goal and scope

Implement issue #481, first cut: a calibration report over a labelled set, plus a deterministic sampler that writes a blank labelling sheet. **Owner decision: stability mode (`--no-cache` re-verification k times) is out of scope.** Open nothing for it; the lead files a follow-up issue.

### Labels file

The labels file is a JSON array of `{run, candidate_id, label, note?}`:
- `run` is a review run id;
- `label` is one of `TRUE`, `TRUE-NOT-WORTH`, `PARTLY`, `FALSE` or `UNCHECKABLE`.

Validate it strictly. On a bad entry, name the entry and the field, and exit 2. A label for a run or candidate the store does not have is listed under `unmatched` and is not counted.

### `review-voice evaluate calibration --labels <file> [--thresholds <yaml-or-json>] [--repository <r>]`

Add it as a subcommand of the existing `evaluate` command (`src/cli/evaluate.ts`, `src/evaluate/*`), in the style of the existing subcommands. It reads stored runs and their score breakdowns from the local store, never the network and never a model. It prints JSON, with `--text` for a readable table. Sections:

1. **Precision by band and by category.**
   - Bands are verifier `technical_confidence` in [0, 0.5), [0.5, 0.6), [0.6, 0.7), [0.7, 0.8), [0.8, 0.9), [0.9, 1.0].
   - Per band and per category it gives n, TRUE, TRUE-NOT-WORTH, PARTLY, FALSE and UNCHECKABLE counts.
   - Precision counts TRUE and TRUE-NOT-WORTH as true and FALSE as false. PARTLY and UNCHECKABLE are excluded from the denominator but reported.
   - Each precision carries a Wilson 95% lower bound.
   - Verified and verifier-rejected candidates are reported separately.
2. **Volume and holds.**
   - Under the current thresholds, as recorded in each breakdown, and, when `--thresholds` is given, under the proposed set re-applied to the stored breakdowns.
   - Findings eligible per review: mean, median and max.
   - Holds by reason: confidence floor, materiality, owner precedent, unverifiable, score, policy, and other.
   - Re-applying thresholds must reuse the scorer's own gate logic, not a re-implementation. If the stored breakdown lacks a field needed to re-gate, count it under `notReapplicable` with the reason. Never guess.
3. **Materiality agreement.** Where a breakdown or verification has `material`, a 2x2 of `material` (true or false) against label (TRUE-NOT-WORTH or TRUE), with agreement and n. Report `n: 0` when the field is absent from the data, which is expected on origin/main.
4. **Rejection audit.** For labelled candidates the verifier rejected (`verified: false`), the share labelled TRUE or TRUE-NOT-WORTH (false rejects), with n and the Wilson bound.

### `review-voice evaluate label-sample --out <file> --n <k> --seed <s> [--repository <r>] [--since <date>]`

It draws a stratified sample of stored candidates:
- strata are band crossed with verified-or-rejected;
- the draw is proportional, with at least one per non-empty stratum when k allows;
- a seeded PRNG makes it deterministic, with no `Math.random`.

It writes a labelling sheet (JSON array). Each item has `run`, `candidate_id`, repository, pull number, head sha, `path:line`, severity, category, the claim, the verifier confidence and verdict, and an empty `label`. The sheet is the labels file format plus context fields, so a filled sheet can be passed straight to `--labels`. Context fields are ignored on input.

## Acceptance criteria

- On a fixture store, the report gives exactly the expected counts for each band and category, and a Wilson lower bound to 3 decimals matching a hand-computed value, for example 8 of 10 giving 0.490. The fixture holds about 20 labelled candidates across three bands, verified and rejected, two categories and four repositories' runs.
- `--thresholds` with a higher floor shows fewer eligible findings per review and more `confidence floor` holds than the current set. Re-gating reuses the scorer's gate function; assert on a case where the two sets differ.
- Materiality agreement reports `n: 0` when no breakdown has `material`, and the right 2x2 when the fixture adds it.
- The rejection audit counts false rejects among `verified: false` candidates.
- `label-sample` with the same seed writes byte-identical files. A different seed gives a different selection. Every non-empty stratum is represented when k is at least the stratum count. The written sheet is accepted by `--labels` as is.
- Malformed labels exit 2 naming the entry, and unmatched labels are listed, not counted.
- A new `test/issue-481-calibration.test.mjs` covers the above.
- `npm run verify` passes, apart from failures that also occur on the untouched baseline. On this machine the process-kill timing tests in `test/issue-277-stoppable-commands.test.mjs`, `test/command-runner.test.mjs` and `test/agent-runner.test.mjs` can fail under load and pass alone.
