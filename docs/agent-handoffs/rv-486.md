## Goal and scope

Implement issue #486. A run recorded by the `review` driver stores candidate context (category, claim, failure mode, path, line, severity) only for the eligible findings. A held candidate keeps only its score breakdown, which has no category or claim, plus a held entry with its text. Record every scored candidate's context instead, so consumers can group held findings by category.

- Find where the driver records a run (`src/review/driver.ts`, the record stage and `recordStage`). Find what it passes as candidates to the store (`src/store/runs.ts`, `candidates_json`).
- Pass every scored candidate, eligible or held, with its context. Mark each entry `held: true` or `false` (or `eligible`), so any consumer that today assumes the field holds only eligible findings can tell them apart.
- Audit every reader of `candidates_json`, and of the `--candidates` file the slash-command `record` path writes. Readers include explain, feedback id assignment, carry, carry-candidates, `--held-from`, and verdict. Make sure none starts treating a held candidate as a posted finding. Feedback ids and posted-finding positions must not change. If a reader can't tell them apart without the new mark, use it.
- `/review-voice:review` step 6 (`commands/review.md`) tells the slash command to pass "the scored candidates, the challenged scores' eligible[]" to `record --candidates`. Update that text to pass all scored candidates with the same mark, keeping the challenge-moved line for eligible ones.
- Old runs keep today's behaviour.
- CHANGELOG entry under Unreleased. Rebuild `dist`. Do not bump the version.
