## Goal and scope

Implement issue #480: outcomes of the tool's own posted findings become precedent, so owner and repository alignment can fall below neutral and the owner-precedent gate can fire. **Approved approach (owner decision): derive them at retrieval time from the stored `finding_outcomes` rows. Write no new precedent rows.** This keeps the change reversible: deleting the outcome rows, or turning the feature off, removes what was learned.

- **Source.** `finding_outcomes` (`src/store/db.ts` around line 225, `src/store/outcomes.ts`), joined to the recorded finding it belongs to (`review_run_id`, `finding_id`) for the finding's repository, path, line, category and claim text. Find where `record` stores findings and read them from there; add no schema unless that is unavoidable, and if it is, stop and say why.
- **Mapping.**
  - A `strong` `dismissed` becomes outcome `dismissed`. That covers a reply that disputes the finding or declines it as not worth it, which `classifyReply` reads as `reject`, and an owner `dismiss` feedback row.
  - A `fixed` becomes `accepted`.
  - Everything else (`weak` anything, `resolved` without a fix, `outdated`, `open`, `unknown`) contributes nothing. Silence is never a dismissal.
- **Role.**
  - `owner` when `decidedBy` is the configured owner reviewer (`identity.owner_reviewer`).
  - `bot` for a Bot account or a login matching the queue's bot author patterns.
  - `team` otherwise.
  - A reply that only echoes a fix, for example "fixed in <sha>", "done" or "addressed" with no other words, counts at most as `team`, even from the owner. Coding agents fix whatever they are asked, so their echo is weak evidence of the owner's taste.
  - Weight: reuse `baseWeight(role, outcome)` and `eventWeight` from `src/retrieval/weights.ts`. Recency is from `checked_at`.
- **Matching.** Outcome precedents join the existing `retrievePrecedents` (`src/retrieval/retrieve.ts`) results. They are matched to the query the same way existing precedents are, so `matchStrength` and `relevance` mean the same thing, and they are subject to the same repository scope (the repository under review plus `repositories.include`). They are also subject to `--exclude-pull`: an outcome on the pull request under review is never precedent for it. Keep the total precedent count bounded as today. Deterministic: the same store and query give the same list.
- **Provenance.** Each such precedent is marked, for example `source: 'outcome'`, so `explain` and the score breakdown can show that alignment came from a learned outcome. Show it in `explain` where precedents are listed.
- **Status.** `status` shows the count of precedents learned from outcomes, split into accepted and dismissed, and the categories with net negative learned precedent, so the owner can see what the tool has learned to stop saying.
- **Docs.** Add `docs/adr/0039-outcomes-become-precedent.md` (0037 and 0038 are taken by branches in flight), short, in the style of its neighbours, citing #480 and the measured fact in the issue (owner alignment never fell below 0.5 across 1,882 breakdowns). Add an index row, a CHANGELOG entry under Unreleased, and a README line where precedents are described. Rebuild `dist`. Do not bump the version.

## Acceptance criteria

- With a store holding one recorded finding (category maintainability, a claim about an unused export) whose outcome is a `strong` `dismissed` decided by the owner, a later candidate in the same repository, with the same category and a similar claim, has owner alignment below 0.5 (`NEUTRAL_ALIGNMENT`). A candidate with an unrelated claim is unaffected.
- With the outcome `fixed`, the same similar candidate's alignment rises above its value with no outcome.
- A `weak` dismissed, `open`, `outdated` or `unknown` outcome changes nothing.
- The same dismissal decided by a Bot login, or by an echo-only reply from the owner, weighs no more than a `team` dismissal. Assert on the precedent's role or weight.
- An outcome on the pull request passed as `--exclude-pull` is not a precedent for that pull request.
- An outcome in a repository outside the scope is not a precedent.
- `explain` marks a learned precedent's source. `status` prints the learned counts and the net-negative categories.
- Existing retrieval, scoring and outcomes tests pass unchanged where they do not involve stored outcomes.
- A new `test/issue-480-outcome-precedent.test.mjs` covers the above.
- `npm run verify` passes, apart from failures that also occur on the untouched baseline. On this machine the process-kill timing tests in `test/issue-277-stoppable-commands.test.mjs`, `test/command-runner.test.mjs` and `test/agent-runner.test.mjs` can fail under load and pass alone.
